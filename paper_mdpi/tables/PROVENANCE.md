# Table provenance

How every number in the `paper_mdpi/tables/*.tex` tables is computed: the source file
of record, the code that produces it, and the aggregation applied.
Each table section has a "Recompute" snippet. The snippet only reads the existing result
files and derives the printed numbers from them; it never re-runs an experiment.
Paths are relative to the repository root. Sections are keyed by LaTeX label, not by
table number, because the numbers shift when the layout changes. Each table section records the commit at
which its numbers were last checked against the source.

All quantitative tables are documented.
(`tab_policy_support` and `tab_threat_guarantee` are qualitative and carry their
sources in their header comments. Four tables are defined inline in section files rather than in
`tables/`: `tab:nmi-sample-size-sensitivity` (`sec_nmi_sensitivity.tex`, documented below), and
the qualitative `tab:duo-categories` (`sec_background.tex`), `tab:related-work-gap`
(`sec_related_work.tex`), and `tab:transcript-normalization` (`sec_design.tex`).)

## Shared: supervised verdict pipeline

Used by `tab_privacy_summary`, `tab_pch_terms`, `tab_pch_icd10`, `tab_pi_pairs`,
`tab_spp_contrasts`.

**Code.** `experiments/analysis/supervised/common.py` (shared logic) plus one driver per
objective (`pch_supervised.py`, `pi_supervised.py`, `spp_supervised.py`). The JavaScript
pipeline (`experiments/core/multiseed_criterion.js`) is an independent cross-check, not
the source of record.

**Generated by** (for reference only; do not re-run during revision, as these commands
overwrite the git-tracked results of record):

```bash
npm run analysis:supervised     # = analysis:pch && analysis:pi && analysis:spp, 30 seeds each
npm run analysis:compare:js     # Python vs JS verdict comparison
```

**Outputs** in `experiments/results/supervised/`: `<exp>_supervised_verdict.json`
(of record), `<exp>_supervised_summary.csv` (flat view), `<exp>_split_manifest.json`
(the exact train/test policies per seed), `<exp>_js_comparison.json`.

**Input.** `experiments/data/polygonAmoy/` (the 1,773 Amoy executions). Features are the
nine public-chain observables in `FEATURE_KEYS`: commit/access gas used, commit/access
calldata length, proof size, and commit/access log count and log size. Features
that are constant on a seed's training split are dropped for that seed.

**Per task, per seed** `s = 0..29` (`analyze_contrast` → `evaluate_seed`):

1. Keep one execution per policy (`one_execution_per_group`), so that policies with
   many executions do not dominate.
2. Draw a policy-disjoint, near-stratified 70/30 holdout
   (`repeated_stratified_group_holdout`): 512 random candidate splits, keeping the one
   whose per-class test ratio is closest to 0.3.
3. Train two classifiers on the training split: logistic regression (standardized,
   `class_weight="balanced"`) and random forest (50 trees, depth 10, balanced).
4. Compute the test AUC (`roc_auc_score`), and the permutation p-value: 500 label shuffles on
   fixed scores, `p = (k+1)/(500+1)`, where `k` counts shuffles with AUC ≥ observed
   AUC.

**Per task, per model** (over the 30 seeds):

- `aucMean` = mean of the 30 per-seed AUCs.
- `sigFraction` = share of seeds with `p < 0.05`, so always a multiple of 1/30.
- The model **fails** the task if `aucMean > 0.55` **and** `sigFraction ≥ 0.5`.
- The **task FAILs if either model fails** (`passed = not any_leg_fails`).
- `nonGating = true` excludes a task from the verdict: when the median test size is
  below 20, or, for PI, when the task is `controlled_difference` (the positive control).

**Reporting convention.** For each task, the tables report the model with the higher
`aucMean` (the stronger attacker), with that model's `sigFraction`. For both current
FAILs, the higher-AUC model is also the one that triggers the failure (see `tab:privacy-summary`).

## `tab:privacy-summary` (`tab_privacy_summary.tex`)

Last checked against the source: results commit `6b45855` (unpadded capture of 2026-10-15), 2026-10-16. The table is

### Recompute

```bash
python3 - <<'PY'
import json, statistics as st
for exp in ["pch", "pi", "spp"]:
    tasks = json.load(open(f"experiments/results/supervised/{exp}_supervised_verdict.json"))["tasks"]
    rows = []
    for t in tasks:
        if t["nonGating"]:
            continue
        m = max(t["models"], key=lambda k: t["models"][k]["aucMean"])
        rows.append((t["key"], t["models"][m]["aucMean"], t["models"][m]["sigFraction"], t["passed"]))
    ok = [r for r in rows if r[3]]
    print(exp, f"{len(ok)}/{len(rows)} pass;",
          f"AUC {min(r[1] for r in ok):.3f}-{max(r[1] for r in ok):.3f};",
          f"median sig {st.median(r[2] for r in ok):.0%};",
          "FAIL:", [r[0] for r in rows if not r[3]])
PY
```

## `tab:corpus` (`tab_corpus.tex`)

Last checked against the source: commit `7c9dd3c` data (`experiments/data/polygonAmoy/`, the unpadded capture of
2026-10-15), 2026-10-16. All cells match. The groupings are set in pairs, side by side: DUO terms beside ICD-10
chapters, then the four SPP groupings two by two, with the corpus total as the last row.

**Source.** `experiments/data/polygonAmoy/executed_dataset.json`: a list of 1,977 records,
one per execution (commit, resource registration and access on chain). Every execution commits its own policy
instance, so `policyId` (the generator's policy) groups executions while `blockchainPolicyId` is unique per record.

**No analysis code produces this table.** It is a direct count over the dataset.

### Columns

- **Policies** = number of distinct `policyId` among the matching records.
- **Executions** = number of matching records.

Executions exceed policies because of the two-layer design: 1,017 *coverage* policies are
executed once (`executionTier == "coverage"`), and the 60 policies of the 30 designed PI pairs are executed
16 times each, 8 granted and 8 denied (`executionTier == "pi"`), giving 1,017 + 60 = 1,077 policies and
1,017 + 960 = 1,977 executions. A row whose two counts are equal, such as `ch2` or `ch7`, contains no PI-layer
policy.

### Rows

Each label field is constant across the executions of one policy (checked), so a policy
belongs to exactly one bucket of each SPP grouping.

| Group | Record field and match rule | Notes |
|---|---|---|
| DUO data-use term | `t in duoTermCodes` | Multi-label: rows overlap, so the column sums exceed the totals. |
| ICD-10 chapter | `ontologyNamespace == "ICD10" and ontologyValue == i` for `ch<i>` | Single-label within the policies that have an ICD-10 scope (the DS policies). |
| Subtotal (ICD-10 group) | `ontologyNamespace == "ICD10"` | Equals the sum of ch0–ch9 and the DS row (422 policies). |
| SPP `structureType` / `nestingDepth` / `predicateCombo` / `paramType` | `record[field] == bucket` | Bucket boundaries are defined in `sec_spp.tex`. Each grouping partitions the corpus, so each sums to 1,077 / 1,977. |
| Corpus total | all records | |

### How the analyses use these counts

- **PCH DUO tasks:** one-vs-rest over all 1,077 policies. The task key in
  `pch_supervised_verdict.json` is `DUO GR` for the term printed here as `GRU`.
- **PCH ICD tasks:** one-vs-rest **within the DS policies** (422 policies, `_icd_chapter` in `pch_supervised.py`).
- **SPP:** `spp_dataset.json` keeps the 1,017 coverage executions and 3 granted and 3 denied executions of each
  PI-layer policy (1,377 executions). The SPP rows here count the full corpus.
- Every supervised task samples one execution per policy per seed, so the effective
  sample size of a task is its **Policies** count, not its Executions count.

## `tab:pch-terms` (`tab_pch_terms.tex`)

Last checked against the source: results commit `6b45855` (unpadded capture of 2026-10-15, granted and denied
executions pooled), 2026-10-16. All 40 cells and the note match.

**Source.** `experiments/results/supervised/pch_supervised_verdict.json`, the 10 entries of
`tasks[]` whose `key` starts with `DUO`. The pipeline is the shared supervised pipeline
above; the driver is `pch_supervised.py` (`build_tasks`), and its input is
`experiments/data/polygonAmoy/pch_dataset.json`, which is byte-identical to
`executed_dataset.json`.

### Task and label

Each row is a one-vs-rest task over all 1,077 policies: the label is 1 if the policy contains the term.
The label rule is `code in _duo_codes(record) or term_id in _duo_ids(record)`, with
`term_id` from `DUO_TERM_ORDER`. Two naming details:

- **`GRU` is keyed `DUO GR`** in the JSON (`DUO_TERM_ORDER` uses `GR`, and
  `DUO_CODE_ALIASES` maps `GRU` → `GR`).
- **The numeric IDs are consistent.** In the data, `semantics.duoTermValues` uses GRU 0, DS 1, RS 2,
  POA 3, GS 4, CC 5, NCU 6, HMB 7, NMDS 8, GSO 9, the same numbering as `DUO_TERM_ORDER`.
  (`attributeOrder` in each record is a different index space and is not used for labels.)
  For every term, the positive policy set equals plain membership in `duoTermCodes`
  (checked). Its sizes are the Policies column of `tab:corpus`.

### Columns

For each row, take the model (LR or RF) with the higher `aucMean`; every cell comes from that
model's entry `models.<m>`:

| Column | Field | Definition over the 30 seeds |
|---|---|---|
| AUC mean | `aucMean` | mean of `perSeed.auc` |
| ± std | `aucStd` | **population** standard deviation of `perSeed.auc` (`np.std`, ddof = 0) |
| AUC gap (mean) | `advantageMean` | mean of `|perSeed.auc − 0.5|` (Eq. `eq:auc-gap`) |
| %sig | `sigFraction` | share of `perSeed.pval < 0.05`, a multiple of 1/30 |

**Table note (test-set size).** The table has no test-size column, because `medianTestN` = 323
for every DUO row: each seed keeps one execution per policy, and the holdout puts
`round(0.3 × 1,077) = 323` policies in the test set. The note states this value and the range
of the median positive test count per task (`splitDiagnostics.classes["1"].medianTestGroups`):

| Term | GRU | DS | RS | POA | GS | CC | NCU | HMB | NMDS | GSO |
|---|---|---|---|---|---|---|---|---|---|---|
| Positive test executions per seed (median) | 91 | 127 | 124 | 118 | 115 | 118 | 62 | 99 | 71 | 71 |

Range 62–127, as stated in the note.

Selected models: LR for GRU, CC, HMB, and NMDS; RF for DS, RS, POA, GS, NCU, and GSO. All 10
tasks pass, and no model meets either leg of the criterion (max `aucMean` 0.535 and max
`sigFraction` 8/30 = 27%, both POA/RF).

### Recompute

The snippet recomputes the summary statistics from the per-seed values, independently
of the stored `aucMean`/`aucStd`/`advantageMean`/`sigFraction`, and asserts that they agree.

```bash
python3 - <<'PY'
import json, statistics as st
v = json.load(open("experiments/results/supervised/pch_supervised_verdict.json"))
for t in v["tasks"]:
    if not t["key"].startswith("DUO"):
        continue
    m = max(t["models"], key=lambda k: t["models"][k]["aucMean"])
    md = t["models"][m]
    aucs, pv = md["perSeed"]["auc"], md["perSeed"]["pval"]
    mean, std = sum(aucs) / len(aucs), st.pstdev(aucs)
    gap = sum(abs(a - 0.5) for a in aucs) / len(aucs)
    sig = sum(p < 0.05 for p in pv) / len(pv)
    assert abs(mean - md["aucMean"]) < 1e-12 and abs(std - md["aucStd"]) < 1e-12
    assert abs(gap - md["advantageMean"]) < 1e-12 and sig == md["sigFraction"]
    name = "GRU" if t["key"] == "DUO GR" else t["key"].split()[1]
    print(f"{name:5s} {m}  {mean:.3f} ± {std:.3f}  gap {gap:.3f}  sig {sig:.0%}  n {t['medianTestN']:.0f}")
PY
```

## `tab:pi-pairs` (`tab_pi_pairs.tex`)

Last checked against the source: results commit `6b45855` (unpadded capture of 2026-10-15), 2026-10-16. All cells
match.

**Source.** `experiments/results/supervised/pi_supervised_verdict.json`, one entry of `tasks[]` per pair type,
produced by `pi_supervised.py` from `experiments/data/polygonAmoy/pi_dataset.json` (the 960 PI-layer executions).
The pairs are the ones the capture was designed with (`piPair` on each record): 10 per type, each policy in one
pair, sides drawn at random (`selectPiPairs` in `experiments/core/data_generator.js`).

### Pair types (generator predicates)

| Type | Rule (`PI_PAIR_PREDICATES`) |
|---|---|
| `semantic_equivalent` | same `logicNormalized`, different `scopeParameters` |
| `weak_equivalent` | same DUO term set, different `logicNormalized` |
| `controlled_difference` | different DUO term sets; 2 pairs at each shape distance 0–4 (number of the four SPP axes on which the policies differ) |

### Protocol and columns

Per seed and pair, half of the executions of every (side, outcome) cell are tested (16 of a pair's 32); one LR and
one RF are trained per pair on the other half; o is not a feature. The pair AUC is over its test executions; the
type statistic is the mean pair AUC; the permutation null shuffles test labels within pairs (500 permutations).

For each row, take the model with the higher `aucMean`:

| Column | Field |
|---|---|
| Pairs | `nPairs` |
| AUC mean ± std | `aucMean`, `aucStd` (population std over the 30 per-seed statistics) |
| AUC gap (mean) | `advantageMean` = mean of `|perSeed.auc − 0.5|` |
| %sig | `sigFraction` |
| med n | `medianTestN` (10 pairs × 16) |
| Control AUC (%sig) | `positiveControl.models.<m>` for the model with the higher control `aucMean` (LR for all three) |

`positiveControl.detected` is true when the control run fails the leakage criterion for either model; a type whose
control is not detected would be INCONCLUSIVE. All three types gate (`controlled_difference` included).
RF on `controlled_difference` has mean AUC 0.442 (below 0.5); the table shows the LR row (0.478), the higher one.

### Recompute

```bash
python3 - <<'PY'
import json, statistics as st
v = json.load(open("experiments/results/supervised/pi_supervised_verdict.json"))

    m = max(t["models"], key=lambda k: t["models"][k]["aucMean"])

    mean, std = sum(aucs) / len(aucs), st.pstdev(aucs)
    gap = sum(abs(a - 0.5) for a in aucs) / len(aucs)

    assert abs(mean - md["aucMean"]) < 1e-12 and abs(std - md["aucStd"]) < 1e-12 and sig == md["sigFraction"]
    c = t["positiveControl"]["models"]; cm = max(c, key=lambda k: c[k]["aucMean"])
    print(f"{t['key']:22s} {m} {mean:.3f} ± {std:.3f} gap {gap:.3f} sig {sig:.0%} n {t['medianTestN']:.0f} "
          f"pairs {t['nPairs']} control {cm} {c[cm]['aucMean']:.3f} ({c[cm]['sigFraction']:.0%}) {t['status']}")
PY
```

Expected output:


### Method (`ensemble_permutation_analysis`)

- **Features: only `commitGasUsed` and `accessGasUsed`**, standardized. The supervised attacks
  use all nine.
- K-Means with K = number of classes, run with 20 seeds (`n_init = 10` each). **ARI and NMI are the means
  over the 20 runs** (`kmeans_ari`, `kmeans_nmi`).
- **p_ARI / p_NMI** (`ari_p_value` / `nmi_p_value`, tabulated to two decimals, ROUND_HALF_UP): the 20 cluster
  assignments are fixed, the labels are permuted 200 times, both metrics are recomputed on each permutation, and
  `p = (#null ≥ observed + 1) / 201`.
- The CSV column `n` (500) is the number of policy-bootstrap iterations behind `ariCi95`/`nmiCi95`,
  **not** a sample size. The table's n is `n_samples`.

| Witness, Prove, Verify | `timings.{witnessMs,proveMs,verifyMs}` → `median` (`p95`), from `generateProof`'s internal timers |
| End-to-end | `timings.totalMs`: wall-clock time of `proveRequest`, i.e. `evidenceFor` (off-circuit evidence) plus `generateProof` |

Medians and p95s use linear interpolation, `quantile()` in the script: position (n − 1)·q. For example, Simple's
end-to-end median is (924 + 926)/2 = 925, and its p95 is 1106 + 0.55 × (1223 − 1106) = 1170.35.

**End-to-end minus (witness + prove + verify), per run (median):** Simple 13 ms, Ontology-heavy 13 ms,
**Profile-heavy 640 ms, Max-mixed 637 ms.** The extra ~630 ms in the two profile-backed policies comes
from `evidenceFor`. For a type-9 (profile) slot, it **issues a fresh signed profile credential for every request**:
`signDuoProfileCredential` in `lib/prover.js` acts as the issuer, and it calls `circomlibjs.buildEddsa()` on every
invocation. In deployment, the issuer signs a credential once and the requester presents it, so this is a
**benchmark-harness cost, not a per-request cost of the protocol**. Allowlist (Merkle) preparation is in the
13 ms of the other rows.

### (b) Load: `load[]`, 100 measured requests per concurrency level

| Column | Field |
|---|---|
| Throughput | `throughputPerSecond` = `requests / wallMs × 1000` (recomputed: 0.805, 0.787, 0.936) |
| Latency | `latencyMs` → `median` (`p95`), each request's `totalMs` while up to c run at once (queueing excluded) |

The four policies rotate, so about half of the requests carry the harness's ~0.64 s credential issuance.
The throughput is therefore conservative.
