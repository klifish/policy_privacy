# Response to Reviewer 1, Comment 2

> **Comment.** The proof must be cryptographically linked to the authorization context. The current
> proof statement is not linked to the requester identity, protected resource, or session context.
> As mentioned in the manuscript, single-use of the nonce does not allow reuse of the same session
> parameters, but it does not prevent replay of a valid proof captured by an active party using
> fresh parameters. This is a significant limitation of the authorization guarantees of the current
> prototype. The authors would ideally add the relevant requester/resource/session values to the
> proved statement and experimentally evaluate the resulting circuit/public-input and gas cost
> changes. If this cannot be implemented in the current version, the security claims and deployment
> implications should be made even more explicit throughout the manuscript, including the abstract
> and conclusion.

**Response.** We thank the reviewer for this comment. We agree, and we have taken the first of the
two options: the authorization context is now bound into the proof statement in the current
implementation, and we report the measured circuit, public-input, and gas cost changes the reviewer
asked for. In preparing the change we also found that our own description of the submitted system
was inaccurate on one point, which we correct below.

## 1. Confirmation and scope of the issue

### 1.1 The gap

The reviewer's description is accurate. In the submitted version the public statement was

```
pubSignals = [isAuthorized, policyCommitment, paramsCommitment]
```

with no component derived from the requester, the resource, or the session. The ACM validated
$(\mathit{id}_{\mathrm{res}}, \mathit{nonce})$ as transaction parameters and enforced nonce
single-use over the tuple `(policyId, resourceId, nonce)`, but nothing tied those parameters to the
proof being submitted alongside them. The statement therefore certified

> "*someone* satisfied the policy committed as $h$"

rather than

> "*this requester* satisfied $h$ *for this resource* in *this session*."

The first form is transferable. As the reviewer notes, nonce single-use does not prevent this,
because the nonce is itself one of the values being changed: a fresh nonce passes the replay check
while the captured proof still verifies.

### 1.2 Who can exploit it

We want to be precise about the adversary, because it bears on severity. In our deployment the TPS
submits the transaction on the requester's behalf, so an arbitrary on-chain party replaying a
captured proof obtains only a record under its own address, outside the workflow through which
resources are actually released. The exploitable cases are therefore:

- a **deviating TPS**, which holds every proof it generates and can submit any of them under a
  different requester, resource, or session; and
- a **compromised TPS key**, which lets an adversary mint authorization records from previously
  observed proofs without being able to generate proofs at all.

Both are the same class of adversary as in comment R1-1, and both fall squarely within what the
manuscript's own discussion of TPS trust concentration identifies as the design's principal risk.
We agree with the reviewer that describing this as a limitation of the authorization guarantees,
rather than deferring it as out of scope for the passive threat model, is the correct framing: the
passive model was drawn to scope the *privacy* evaluation, and using it to excuse a soundness gap
in *authorization* would be a category error on our part.

### 1.3 An inaccuracy in the submitted manuscript

While implementing the fix we found that one statement in the submitted version was wrong, and we
report it rather than quietly correcting it. Section 3 stated that an authorization is bound to
$\mathit{id}_{\mathrm{req}}$ "in the current implementation, at the transaction level rather than
inside the proof statement." That is not what the submitted code did. The contract recorded
`msg.sender` as the requester, and `msg.sender` is the TPS, since the TPS submits on the requester's
behalf specifically so that the requester's address never appears on-chain. The submitted system
therefore had **no representation of requester identity anywhere on the chain path** — not in the
statement, and not at the transaction level either. The gap was thus one step wider than our own
disclosure described. The revision introduces a requester pseudonym as an explicit parameter and
binds it into the statement, which closes the gap and makes the corrected description accurate.

## 2. Change to the construction

The proof statement now carries a fourth public signal, the authorization-context digest

```
ctx = Poseidon(id_req || id_res || nonce)
```

so the statement becomes `[isAuthorized, policyCommitment, paramsCommitment, ctx]`. The three
context values are **private witness inputs**; only their digest is public. In-circuit, the digest is
enforced by a hard equality constraint rather than folded into the authorization output, so a
witness whose context triple disagrees with the committed digest fails witness generation outright
instead of merely yielding `isAuthorized = 0`.

We chose the digest form over exposing the three values as separate public inputs for two reasons,
both of which matter for this paper specifically:

1. **It preserves requester anonymity.** The design deliberately keeps the requester's identity off
   the chain. Publishing $\mathit{id}_{\mathrm{req}}$ as a public input would place it in calldata,
   visible to exactly the metadata-only adversary the paper evaluates, and would weaken a property
   the construction is built to provide. Under the digest form the requester pseudonym is bound to
   the proof without being disclosed.
2. **It costs one public input instead of three**, which keeps the verifier-gas increase small
   (Section 3) and limits the perturbation to the transcript that the privacy evaluation measures.

The binding is enforced on both sides. In-circuit, the hard equality ties the digest to the context
values the prover actually used. On-chain, the ACM recomputes
$\mathsf{Poseidon}(\mathit{id}_{\mathrm{req}} \parallel \mathit{id}_{\mathrm{res}} \parallel
\mathit{nonce})$ from the transaction parameters and requires it to equal the proof's fourth public
signal, reverting otherwise. The two checks close different gaps, and we implemented both: the
in-circuit constraint makes a proof non-transferable, so it verifies only for the context it was
generated for; the on-chain recomputation additionally prevents a recorded request from *citing* a
statement proved for a different context, which a submitter could otherwise do by pairing a genuine
proof with unrelated transaction parameters.

Recomputing Poseidon in the EVM is the more expensive half of the change (Section 3), and we
considered omitting it and relying on the circuit constraint alone. We kept it because the resulting
guarantee is the one the reviewer asks for — the authorization context is verified against the proof
at the point of record, not merely asserted alongside it — and because the alternative would leave
an auditor, rather than the contract, responsible for detecting inconsistent records. To keep the
on-chain hash identical to the circuit's, the hasher is deployed from circomlib's generated EVM
bytecode rather than reimplemented in Solidity; a regression test pins the agreement between the two
implementations.

The nonce-replay key was extended to `(policyId, resourceId, nonce, id_req)` accordingly, so its
scope matches the granularity of the binding: a nonce consumed for one requester cannot be reused to
record an authorization for another, and replaying a requester's own exact tuple is still rejected.

## 3. Cost of the change

The reviewer asked for the circuit, public-input, and gas cost changes to be evaluated
experimentally. Measured values:

**Circuit and verification interface.**

| | Submitted | Revised | Change |
|---|---:|---:|---:|
| Non-linear constraints | $37{,}865$ | $38{,}129$ | $+264$ |
| Linear constraints | $37{,}320$ | $37{,}661$ | $+341$ |
| Total R1CS constraints | $75{,}185$ | $75{,}790$ | $+605\ (+0.8\%)$ |
| Public inputs | $2$ | $3$ | $+1$ |
| Verifier gas | $228{,}754$ | $235{,}914$ | $+7{,}160\ (+3.1\%)$ |

Verifier gas was measured by deploying both the submitted verifier and the regenerated verifier and
calling each on the same proof points, so the figure isolates the marginal cost of the additional
public input: one extra G1 scalar-multiply-accumulate in the public-input aggregation, ahead of an
otherwise unchanged pairing check. Calldata grows by one 32-byte word.

**On-chain digest recomputation.** The ACM's Poseidon(3) call costs $49{,}298$ gas, measured as the
internal `staticcall` the access path actually performs (excluding the transaction base fee). This
is the dominant part of the change and reflects the cost of a ZK-friendly hash in the EVM. We report
it separately because it is the price of the stronger guarantee discussed in Section 2 rather than
of the binding itself: an implementation that relied on the in-circuit constraint alone would incur
only the $+7{,}160$ above.

**End-to-end.** A complete `requestAccessBound` call with a valid proof — verification, digest
recomputation, and record write — consumes $537{,}986$ gas in a local EVM. The two components above
account for $+56{,}458$ of that relative to the submitted access path, plus a small fixed cost for
the two additional words stored in each access record.

Unlike the program-length binding of comment R1-1, which left the public-signal count at two and
therefore did not perturb the verification interface, this change moves it. We accordingly
regenerated the proving and verification keys and re-ran the of-record evaluation rather than
arguing that the measurements were unaffected; the gas-channel results in particular are re-derived
from the new runs, since both the padding target and the underlying access gas shift. The
transcript-normalization design is unaffected in kind: the added cost is constant across policies,
so the padded profile remains policy-independent.

## 4. Validation

We added regression tests covering both halves of the binding.

`test/context_binding_test.js` covers the in-circuit half: it establishes that the digest separates
contexts differing in the requester, in the resource, and in the nonce individually; that a statement
bound to one context does not authorize under any of the three substitutions; and that an honestly
re-proved request in a new session still authorizes, so the binding does not break legitimate
re-authorization.

`test/context_binding_onchain_test.js` covers the ACM half: it pins the agreement between the
on-chain hasher and the circuit's digest across several inputs — everything else depends on that
agreement — and establishes that a request citing a proof bound to a different requester, resource,
or session reverts, that a matching request proceeds to verification, and that nonce single-use is
now scoped per requester.

To confirm the test exercises the vulnerability rather than passing vacuously, we rebuilt the
submitted circuit from version control and ran the attack against it. On the submitted construction
the honest witness yields `isAuthorized = 1` under a two-signal public statement that contains no
context component whatsoever; the identical proof tuple therefore verifies for any
$(\mathit{id}_{\mathrm{req}}, \mathit{id}_{\mathrm{res}}, \mathit{nonce})$ a submitter chooses, and
the replay succeeds. Under the revised construction every substitution is rejected. Proof generation
and on-chain verification were re-run end to end against the rebuilt circuit and the regenerated
verifier.
