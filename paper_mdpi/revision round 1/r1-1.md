# Round 1, Comment 1 — Unbound program length

**Status:** code fix complete (commit `a5586b2`, branch `revision/mdpi-blockchains-r1`).
Manuscript text and of-record evaluation data **not yet updated** — see [Outstanding work](#outstanding-work).

---

## Reviewer comment

> The security implications of the unbound program length should be more strongly addressed.
>
> According to the manuscript, the preimage of the commitment does not include the length of the program ℓ. Thus, a TPS that deviates from the prescribed workflow may consider a stack-consistent prefix of the committed token array instead of the full desired policy. This is not an implementation detail, but a matter of soundness. The proposed framework is oriented toward verifiable consent enforcement and therefore the authors should either bind the program length in the commitment/proof relation in the current implementation or give a much stronger justification for postponing this modification.

---

## Assessment

The comment is correct, and we accepted it in full rather than arguing for postponement.

Three facts were verified against the source before making any change:

1. **ℓ was absent from the preimage.** The commitment was `h = Poseidon(Poseidon(P) ‖ r)`
   (`circuits/gadgets/policy_commitment.circom`, `compiler/policy_generator.js`).
2. **ℓ was a free private witness.** `numOperations` was an ordinary circuit input
   (`circuits/policy_privacy_main.circom:76`), and the deployed instantiation declares only
   `public [policyCommitment, paramsCommitment]` — so ℓ was neither hashed nor exposed.
3. **The only global stack constraint is `sp[DEPTH] === 1`**
   (`circuits/interpreter/postfix_policy_interpreter.circom:318`). Every RPN program reaches
   stack depth 1 after its first operand, so many prefixes satisfy it.

The previous manuscript disclosed this in §4.3 and deferred the fix to future work. Since the
reviewer raised the objection *after reading that disclosure*, restating it more forcefully was
not a viable response. The framework is presented as *verifiable* consent enforcement; if policy
semantics ultimately rest on trusting the TPS not to cheat, that claim is materially weakened.
The fix also turned out to be cheap (below), which further undercuts any case for deferral.

### The exploit is stronger than "re-interpretation"

Worth stating precisely, because the obvious construction does **not** work.

Truncation must leave the *skipped* tokens satisfying the per-step arity constraints, which are
**not** masked by the `active` flag: `isBinary[i] * (1 - have2[i]) === 0` is enforced at every
index. So truncating a binary operator (`A AND B` → `A`) is rejected by the arity check, not by
length binding — that case passed both before and after the fix and is **not** evidence of the
vulnerability.

The working construction truncates before a *unary* operator:

| | Committed program | ℓ | Program evaluated | Requester holds `attr3` | `isAuthorized` |
|---|---|---|---|---|---|
| Honest | `[attr3, NOT]` | 2 | `NOT attr3` | yes | **0** (deny) |
| Attack | `[attr3, NOT]` | 1 | `attr3` | yes | **1** (allow) |

`NOT` is unary and requires only stack depth ≥ 1, so index 1 remains satisfiable while inactive.

Measured on the pre-fix circuit, the truncated witness **flips `isAuthorized` from 0 to 1**. The
deviating TPS does not merely reinterpret the policy — it obtains an authorization the committed
policy denies. This is worth stating plainly in the response letter.

## Change made

The commitment now binds the program length:

```
h = Com(P, ℓ; r) = Poseidon(Poseidon(P) ‖ ℓ ‖ r)      (was: Poseidon(Poseidon(P) ‖ r))
```

**Circuit**
- `circuits/gadgets/policy_commitment.circom` — both templates take a `programLength` input.
  `PolicyCommitmentVerifier`: `Poseidon(2)` → `Poseidon(3)`. `PolicyCommitmentVerifierDirect`:
  direct-hashing threshold `DEPTH ≤ 15` → `DEPTH ≤ 14`, tree path `Poseidon(2)` → `Poseidon(3)`.
- `circuits/policy_privacy_main.circom` — `numOperations` is wired into the commitment verifier,
  so the length checked by the interpreter is the length bound by the commitment.
- `circuits/interpreter/postfix_policy_interpreter.circom` — corrected a stale comment that
  described `numOperations` as a public input.

**Host code** — all three implementations of the scheme updated in step:
`lib/prover.js`, `test/utils/proofGenerator.js`, `compiler/policy_generator.js`.

`calculatePolicyCommitment(policy, randomizer, programLength)` takes the length as a **required,
range-validated** argument. Defaulting was deliberately avoided: a silent default would produce a
commitment the circuit rejects, surfacing as an opaque proof failure. Making it mandatory
surfaced roughly ten call sites across the SDK, API, experiment harness, and tests, each updated
to pass the length that actually reaches the circuit.

### Cost

| Metric | Before | After | Δ |
|---|---:|---:|---:|
| Non-linear constraints | 37,844 | 37,865 | +21 |
| Linear constraints | 37,253 | 37,320 | +67 |
| **Public inputs** | **2** | **2** | **0** |

About 0.06% of the ~75k-constraint system. **The public signal count is unchanged**, so ℓ remains
private and on-chain verifier gas is unaffected — the hardening costs neither policy
confidentiality nor the policy-independent verification interface. Both points belong in the
response letter.

## Test evidence

`test/program_length_binding_test.js` — 6 cases, all passing.

- Commitment level: length is part of the preimage (same tokens + randomizer, different ℓ ⇒
  different `h`); a missing length is rejected; an out-of-range length is rejected.
- Circuit level: the honest program denies; **a truncated prefix does not authorize**.

**Reverse-verified.** Reverting the circuit and host code to the pre-fix scheme makes
*"does not authorize a truncated prefix"* **fail** with the forged authorization, and it passes
after the fix. It is a genuine regression guard, not a test that merely passes.

Two caveats recorded so the response letter stays accurate:

- `commitmentValid` is AND-ed into the output as a soft boolean rather than a hard constraint, so
  the defense manifests as `isAuthorized = 0`, not as witness-generation failure. The test asserts
  *"must not be 1"*, which admits either defense.
- The binary-operator case passes both before and after the fix (blocked by arity constraints, as
  explained above). It is kept for coverage but must **not** be cited as evidence.

**Regression run:** 80 passing / 0 failing across the new test, SDK prover, compiler, and
commitment-gadget suites; the gadget suite exercises real Groth16 proof generation and
verification against the rebuilt circuit. An end-to-end check confirms the compiler → prover →
circuit path agrees on the new commitment.

Pre-existing failures in `test/PolicyPrivacyIntegration*` (`ethers is not defined`, missing
hardhat runtime) were compared against baseline and are unrelated to this change.
