# Response to Reviewer 1, Comment 1

> **Comment.** The security implications of the unbound program length should be more strongly addressed.
>
> According to the manuscript, the preimage of the commitment does not include the length of the program ℓ. Thus, a TPS that deviates from the prescribed workflow may consider a stack-consistent prefix of the committed token array instead of the full desired policy. This is not an implementation detail, but a matter of soundness. The proposed framework is oriented toward verifiable consent enforcement and therefore the authors should either bind the program length in the commitment/proof relation in the current implementation or give a much stronger justification for postponing this modification.

**Response.** We thank the reviewer for identifying this soundness issue. We agree and have adopted the first proposed remedy: the program length is now bound in the commitment and proof relation in the current implementation.

In the submitted construction, the commitment was

```text
h = Poseidon(H_pol(P_enc) || r),
```

while the program length ℓ was used by the interpreter but was not bound to that commitment. A deviating TPS that knew the opening could therefore attempt to evaluate a stack-consistent prefix under the commitment to the full padded token array. This is security-critical because it can reverse an authorization outcome. For example, for a requester satisfying `A`, the committed RPN program `[A, NOT]` with ℓ = 2 denies, whereas the prefix `[A]` with ℓ = 1 grants.

We changed the construction to

```text
q = H_pol(P_enc)
h = Com(P_enc, ℓ; r) = Poseidon(q || ℓ || r),
```

where `H_pol` is the circuit's fixed-length Poseidon aggregation. The same private `numOperations` value is now wired to both the commitment verifier and the RPN interpreter. Consequently, evaluating a different prefix requires opening `h` to a different `(P_enc, ℓ)` pair, which is excluded by the commitment's binding property under the collision resistance of Poseidon. The length remains private and this modification adds no public proof input.

We also added a dedicated regression suite. It verifies that (i) the same padded token array and randomizer produce different commitments for different lengths, (ii) a missing or out-of-range length is rejected, (iii) the honest `[A, NOT]` program denies when `A=1`, (iv) its prefix authorizes when separately committed at length one as a positive control, and (v) the truncated length cannot authorize under the commitment to the full program. All seven regression tests pass. We additionally verified the frozen RC1 release manifest and cryptographic artifacts; the manifest records the production commitment as `Poseidon3(policyHash, programLength, randomizer)` with `programLengthBound: true`. These RC1 artifacts were used for the of-record experiments, so the commitments and reported measurements were regenerated under the corrected relation.

The isolated circuit change adds 21 non-linear and 67 linear constraints (88 constraints in total, approximately 0.12% relative to the submitted 75,097-constraint circuit) and adds no public input. Thus, binding ℓ neither reveals the program length nor changes the policy-independent verification interface. Other independent revisions change the absolute circuit size and public-signal layout reported for the final revised system; the figures here isolate only the effect of program-length binding. Existing commitments and proving/verification keys from the submitted relation are incompatible with the revised relation and were regenerated.

The manuscript has been revised as follows:

- **Design, “Commitment Binding and Proof Generation.”** We now define `Com(P_enc, ℓ; r)`, identify the encoded policy as the pair `(P_enc, ℓ)`, and state that the same private length is used in both commitment verification and policy interpretation.
- **Discussion.** We clarify that binding the active program length prevents an authorizing proof from being based on a shorter valid prefix, and distinguish this integrity guarantee from the metadata-privacy evaluation.
- **Conclusion.** We remove the former statement that binding the program length remains future work; the corrected construction and its security implication are presented in the Design and Discussion sections.
