# Response to Reviewer 1, Comment 1

> **Comment.** The security implications of the unbound program length should be more strongly addressed.
>
> According to the manuscript, the preimage of the commitment does not include the length of the program ℓ. Thus, a TPS that deviates from the prescribed workflow may consider a stack-consistent prefix of the committed token array instead of the full desired policy. This is not an implementation detail, but a matter of soundness. The proposed framework is oriented toward verifiable consent enforcement and therefore the authors should either bind the program length in the commitment/proof relation in the current implementation or give a much stronger justification for postponing this modification.

**Response.** We thank the reviewer for this observation. We agree, and we have taken the first of
the two options: the program length is now bound in the commitment relation in the current
implementation. We also agree with the framing — this is a soundness matter, not an implementation
detail — and on re-examination we found the consequence to be more severe than our original
disclosure conveyed. We describe the analysis, the change, its cost, and the resulting revisions
below.

## 1. Confirmation and severity of the issue

The reviewer's description is accurate. In the submitted version the commitment was
`h = Poseidon(Poseidon(P) ‖ r)`, the program length ℓ was an unconstrained private witness, and the
interpreter's only global stack constraint is that the final stack depth equals one. Because every
well-formed RPN program reaches stack depth one after its first operand, many proper prefixes of a
committed token array satisfy that constraint, so a deviating TPS could evaluate a prefix under the
commitment published for the full policy.

In quantifying the exposure we found that the attack is not limited to reinterpretation: it can
invert an authorization decision. Consider the committed policy `NOT attr3`, encoded as the token
array `[attr3, NOT]` with ℓ = 2, and a requester who holds `attr3`. Truncating to ℓ = 1 leaves the
program `attr3`. The honest policy denies the request, whereas the truncated prefix grants it:

| | Committed array | ℓ used | Program evaluated | Decision |
|---|---|---|---|---|
| Prescribed workflow | `[attr3, NOT]` | 2 | `NOT attr3` | deny |
| Deviating TPS | `[attr3, NOT]` | 1 | `attr3` | **grant** |

We verified this against the submitted circuit: the truncated witness changes the authorization
output from 0 to 1. A deviating TPS could therefore obtain an authorization that the committed
policy denies, which is precisely the property the framework is meant to make verifiable. This
strengthens the reviewer's point and, in our view, rules out postponing the fix.

We note one subtlety, since it bears on the scope of the vulnerability. The per-step arity
constraints are enforced at every index of the fixed-length array, including inactive positions.
A truncation that leaves a binary operator among the skipped tokens is therefore already rejected,
because the operator's stack-depth requirement is not met. The exploitable truncations are those
whose skipped tokens remain individually satisfiable — for instance, prefixes ending immediately
before a unary operator, as in the example above. The gap was thus narrower than an arbitrary
choice of ℓ, but, as shown, it was still sufficient to invert a decision.

## 2. Change to the construction

The program length is now part of the commitment preimage:

```
h = Com(P, ℓ; r) = Poseidon(Poseidon(P) ‖ ℓ ‖ r)
```

and the length supplied to the interpreter is constrained to be the same value that is bound by the
commitment. A prover can therefore no longer evaluate the committed token array at any length other
than the one fixed at commitment time; a prefix now requires a second opening of `h`, which
contradicts the binding property of Poseidon. The commitment consequently binds the policy program
— the token array together with its length — rather than the token array alone.

## 3. Cost of the change

The hardening is inexpensive and, importantly, does not affect the verification interface:

| | Submitted | Revised |
|---|---:|---:|
| Non-linear constraints | 37,844 | 37,865 |
| Linear constraints | 37,253 | 37,320 |
| Public inputs | 2 | 2 |

The added length input increases the constraint system by about 0.06%. The number of public signals
is unchanged, so ℓ remains a private witness: the length is bound without being disclosed, on-chain
verifier gas is unaffected, and the policy-independent verification interface — a single circuit
serving all policies — is preserved. The change therefore costs neither policy confidentiality nor
the reusability property that the design is built around.

## 4. Validation

We added a regression test covering the attack. It establishes that the commitment separates
programs that differ only in ℓ, that the prescribed workflow still evaluates the full policy
correctly, and that the truncation above no longer yields an authorization. To confirm the test
actually exercises the vulnerability rather than passing vacuously, we ran it against the submitted
construction, where the truncation case fails by producing the forged authorization; it passes under
the revised construction. Proof generation and on-chain verification were re-run end to end against
the rebuilt circuit.

- **Section 4.2** — The commitment is defined as `Com(P, ℓ; r) = Poseidon(P ‖ ℓ ‖ r)`, and the
  commitment signature and witness description now include the program length.
- **Section 4.3** — The passage stating that ℓ is not part of the preimage, that supplying the
  correct length is part of the prescribed TPS workflow, and that binding ℓ is left to future work
  has been replaced by a statement of the implemented binding. The binding property is now stated
  over the policy program rather than the token array.
- **Section 1 (contributions)** — The second contribution previously qualified faithful witness

  are no longer conditional in this respect, and the claim has been adjusted accordingly. We have

- **Evaluation** — Because the commitment preimage changed, all committed values were regenerated
  and the reported measurements re-derived from the rebuilt circuit and re-run experiments.
