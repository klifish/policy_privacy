# 统一数据集工作流程

## 概述

为了降低链上执行成本，三个实验（PCH、SPP、PI）共享同一个数据集。工作流程分为两个阶段：

1. **验证阶段**：生成策略定义，验证是否满足所有实验的需求（无链上执行成本）
2. **执行阶段**：通过验证后，执行链上操作，收集区块链特征

## 使用方法

### 步骤1: 运行验证脚本

```bash
cd experiments
node unified_dataset_validator.js
```

这会：
- 生成200个策略定义（不执行链上操作）
- 验证是否满足PCH、SPP、PI的所有需求
- 生成`validation_results.json`报告

### 步骤2: 检查验证结果

```bash
cat validation_results.json
```

查看输出：
```json
{
  "config": { ... },
  "results": {
    "pch": { "passed": true, "issues": [] },
    "spp": { "passed": true, "issues": [] },
    "pi": { "passed": true, "issues": [] }
  },
  "allPassed": true
}
```

### 步骤3: 如果验证失败

查看具体的失败原因，调整配置：

```bash
# 复制示例配置
cp unified_dataset_config.example.json my_config.json

# 编辑配置
vim my_config.json

# 使用自定义配置重新验证
node unified_dataset_validator.js --config=my_config.json
```

常见调整：
- **PCH失败**：增加`policyCount`或调整DUO术语的生成权重
- **SPP失败**：调整策略生成逻辑以增加特定维度的覆盖
- **PI失败**：增加语义多样性，确保有足够的不同类型策略

### 步骤4: 验证通过后执行链上操作

验证通过后，使用相同配置运行实际实验：

```bash
# 运行PCH实验（会执行链上操作）
cd policy_content_hiding
node run_experiment.js --config=../my_config.json

# 或运行SPP实验
cd ../structure_and_parameter_privacy
node run_experiment.js --config=../my_config.json

# 或运行PI实验
cd ../policy_indistinguishability
node run_experiment.js --config=../my_config.json
```

**重要**：三个实验应该使用相同的配置（特别是`seed`参数）来确保生成完全相同的策略。

## 配置参数

### 基础参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `policyCount` | 200 | 生成的策略数量 |
| `executionsPerPolicy` | 5 | 每个策略的执行次数 |
| `satisfyRatio` | 0.5 | 满足策略的执行比例 |
| `seed` | `"unified-validation-2024"` | 随机种子（确保可复现） |

### PCH验证阈值

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `validation.pch.minPoliciesPerDUO` | 20 | 每个DUO术语的最小策略数 |
| `validation.pch.minMaxRatio` | 0.4 | 最小/最大比率阈值 |

### SPP验证阈值

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `validation.spp.minPoliciesPerCategory` | 15 | 每个类别的最小策略数 |
| `validation.spp.minMaxRatio` | 0.3 | 最小/最大比率阈值 |
| `validation.spp.maxCV` | 0.6 | 最大变异系数 |

### PI验证阈值

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `validation.pi.minPairsPerType` | 30 | 每种配对类型的最小数量 |
| `validation.pi.minSemanticDiversity` | 0.6 | 最小语义多样性 |

## 验证指标说明

### PCH指标

- **DUO分布**：每个DUO术语的策略数量
- **Min/Max比率**：最少的DUO术语数量 / 最多的DUO术语数量
  - 1.0 = 完美平衡
  - 0.4+ = 可接受
  - <0.3 = 不平衡，需要调整

### SPP指标

对于5个维度（逻辑结构、嵌套深度、谓词数量、集合大小、范围宽度）：

- **分布**：每个类别的策略数量
- **Min/Max比率**：最少类别 / 最多类别
  - 0.3+ = 可接受
  - <0.3 = 不平衡
- **变异系数(CV)**：标准差 / 均值
  - <0.3 = 非常平衡
  - 0.3-0.6 = 可接受
  - >0.6 = 不平衡

### PI指标

- **语义多样性**：1 - 平均语义相似度
  - 0.6+ = 足够多样
  - <0.6 = 需要更多多样性
- **配对类型分布**：
  - `semantic_equivalent`: 语义等价对
  - `structural_variant`: 结构变体对
  - `weak_equivalent`: 弱等价对
  - `controlled_difference`: 受控差异对

## 故障排查

### 问题1: PCH DUO分布不均

**症状**：某些DUO术语的策略太少

**解决方案**：
1. 增加`policyCount`（例如从200增加到300）
2. 调整语义层配置，增加缺少的DUO组合

### 问题2: SPP某个维度不平衡

**症状**：例如"deep nesting"策略太少

**解决方案**：
1. 修改策略生成逻辑，增加复杂策略的权重
2. 在`semanticLayers`中添加专门的复杂策略层

### 问题3: PI语义多样性不足

**症状**：策略太相似，无法形成足够的配对类型

**解决方案**：
1. 增加`policyCount`
2. 增加DUO组合的多样性
3. 增加结构参数的变化范围

### 问题4: 生成时间过长

**症状**：验证脚本运行超过5分钟

**解决方案**：
1. 验证阶段不应该很慢（因为没有链上执行）
2. 检查是否有bug导致死循环
3. 考虑减少`policyCount`进行快速测试

## 成本估算

### 验证阶段（阶段1）
- **时间成本**：2-5秒
- **Gas成本**：0（无链上操作）

### 执行阶段（阶段2）
- **时间成本**：根据网络，10-30分钟
- **Gas成本**：
  - 部署：~4,500,000 gas
  - 每次commit：~250,000 gas
  - 每次access：~650,000 gas
  - 总计：200策略 × 5次 × ~900,000 gas = ~900M gas
  - 如果gas price = 20 gwei，在以太坊主网约18 ETH
  - **建议使用测试网或本地网络**

## 最佳实践

1. **先验证，后执行**：永远不要跳过验证阶段
2. **使用相同的seed**：三个实验必须使用相同的配置和seed
3. **保存配置文件**：成功的配置应该保存并版本控制
4. **增量测试**：先用小数据集测试（例如20个策略），验证流程正确后再放大
5. **使用测试网**：在正式执行前，先在测试网验证完整流程

## 输出文件

- `validation_results.json` - 验证报告
- `executed_dataset.json` - 执行后的完整数据集（包含区块链特征）
- `pch_dataset.json` - PCH实验专用数据集（带标注）
- `spp_dataset.json` - SPP实验专用数据集（带5维度分类）
- `pi_dataset.json` - PI实验专用数据集（带配对信息）
